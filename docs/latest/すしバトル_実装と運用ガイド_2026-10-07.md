# すしバトル — 実装と運用ガイド

更新日：2026年10月7日。改善版のリポジトリ実装に基づく開発・配置の案内です。実行結果の記録とは分けて読み、最新の公開状態は Actions と公開画面で確認してください。

## 1. 全体構成

ブラウザの画面は React・TypeScript・Vite、寿司の3Dは Three.js と React Three Fiber で構成します。対戦ルールを共通の処理へ分け、ローカル対戦とオンライン対戦から利用しています。

オンラインの部屋と対戦状態は Node.js のメモリに保持します。ローカル開発の標準通信は Socket.IO、GMS公開環境では PHP を窓口にした短いHTTP要求とポーリングです。PHPは決まった Node.js の処理へ中継し、ゲームルールは Node.js 側で判定します。

| 場所 | 主な役割 |

| src/data/sideMenus.ts | サイドメニューの価格・効果説明・再購入条件 |
| src/game/battleRules.ts | ダメージ、カード効果、コンボ、防御の共通ルール |
| src/game/matchEngine.ts | 試合状態の更新、手番、山札、勝敗、追加注文 |
| src/features/draft/draftEngine.ts | 購入、共通注文枠、大将のおすすめ、期限・予算検証 |

## 2. ローカルで動かす

開発・ビルド環境は CI に合わせた Node.js 24 を基準にします。初回または依存変更時は、プロジェクトルートで依存を入れます。

```bash
npm ci
npm run dev
```

オンラインも試す場合は別のターミナルで起動します。

```bash
npm run server:dev
```

開発サーバーのURLは Vite が表示します。ポートを固定する場合は `npm run dev -- --host 127.0.0.1 --port 5178` です。画面だけではオンラインの部屋は動かず、対戦サーバーも必要です。

対戦サーバーは標準で `127.0.0.1:3001` に待ち受けます。`HOST`、`PORT`、`SUSHI_ALLOWED_ORIGINS` で接続設定を指定します。PHP通信の画面をローカルで試すときは `VITE_ROOM_TRANSPORT=php npm run dev` を使用します。Viteの中継確認と、実際のPHP実行確認は別の検証です。

### 確認用の入口

| URL末尾 | 用途 |
| --- | --- |
| / | 通常のタイトル・モード選択 |
| /#online | オンライン対戦 |
| /#improvements-demo | 改善したモデル・注文・防御・遊び方の確認 |
| /#mobile-demo | モバイル向け購入画面の確認 |
| /#vertical-draft-demo | 縦方向の購入画面の確認 |

ハッシュはアプリ初期化時に読むため、別の確認画面へ切り替えるときは目的のURLを開き直します。通常対戦の動作確認は、デモの表示確認とは別に行います。

## 3. データ変更時に揃えるもの

カードを変更するときは、データ、対戦ルール、効果文、カードイラスト、3Dモデルの整合を確認します。購入価格、消費AP、攻撃、持続ターンは別の値です。`fullness` は持続型の残存ターンを初期化するためにも使われており、プレイヤーのお腹を直接示す値ではありません。

カードの `base` はネタの判定、`archetype` は赤身・巻物・軍艦などのタグです。軍艦には巻物タグもあります。太巻きは兼用ネタを持ちますが、赤身三種盛りのマグロを代用しません。訳ありカードも元のIDを保ち、効果やコンボの所属を維持します。

購入処理は、予算・20枚上限・期限・二重操作・共通3回枠を検証してから更新します。特急、大将のおすすめ、サイドは同じ注文残数を使います。失敗時は消費せず、大将の抽選は購入成立後に一度だけ行い、オンラインでは結果を状態として保持します。

山札確認では本人の残りカードだけを集計します。山札の順序、相手の手札、参加用トークンを公開状態へ混ぜないようにします。クライアントだけの確認で済ませず、オンラインの操作はサーバーでも手番・AP・所有権・再送を検証します。

## 4. 検証の使い分け

| コマンド | 確認すること |
| --- | --- |
| npm test | 主要ルール、CPU、購入、防御、効果、デッキ表示など |
| npm run typecheck:server | サーバー側の型 |
| npm run test:online | 部屋、オンライン購入、同期、HTTP通信、各種効果 |
| npm run lint | 静的なコード検査 |
| npm run build | フロントの型確認と公開用ビルド |
| node --test scripts/test-auto-merge.mjs | 自動マージ条件 |
| php -l deploy/gms/api.php | PHP構文 |
| node --import tsx scripts/test-php-bridge.mjs | PHP中継の動作 |

日常の変更は関係するテストを選び、失敗・変更・未解決の懸念がない限り同じ確認を繰り返しません。公開用CIは上記に加え、配置と復旧のローカルテスト、配布物作成まで実行します。

見た目はビルド成功だけでは判断できません。寿司の3Dを斜め・横・上から見て、カードサイズのアイコンも確認します。モバイル幅ではボタン、本文、スクロール範囲が収まるかを見ます。今回の粒の配置や文字サイズは、実際の画面で確認する対象です。

公開前後は、別ブラウザの2画面で部屋参加、購入、召喚、ターン交代、防御、再読み込み後の復帰を確認します。公開PHPが応答しても、それだけで対戦全体を確認したことにはなりません。

## 5. GitHubから公開まで

通常は変更をブランチへコミットし、mainへのPRで検証します。同一リポジトリの通常PRは、チェック成功後に `Merge verified pull requests` がマージを試みます。Draftは自動マージ対象外です。必須レビュー・ブランチ保護・競合などの条件は引き続き適用されます。

mainへのpushで `Build and deploy to GMS` が動きます。`GMS_AUTO_DEPLOY=true` の場合はテスト・ビルド成功後に転送と再起動へ進みます。自動マージ側も、検証済みSHAを確認してから配布ワークフローを明示的に呼び出します。ローカルで保存またはコミットしただけでは公開されません。

手動実行の `operation: check` は接続・配置の準備を調べ、ファイル転送や再起動をしません。`operation: deploy` は配布と起動を行います。Secretsや鍵の初回手順は、現役の配置資料を参照してください。

| 配布に関係する場所 | 用途 |
| --- | --- |
| https://gms.gdl.jp/~ryom13/sushi-battle/ | 公開ゲーム |
| https://gms.gdl.jp/~ryom13/sushi-battle/api.php | 公開通信の確認 |
| /home/h0/ryom13/public_html/sushi-battle | 公開画面 |
| /home/h0/ryom13/.sushi-battle-deploy | 配布履歴、専用PM2情報、アーカイブ |
| 127.0.0.1:3001 | 対戦プログラムの待受 |

PM2は対戦プログラムをターミナルとは別に動かします。OS全体の設定や、他のアプリのプロセスを変更する構成ではありません。サーバー本体の再起動後に自動起動するOS設定は本構成に含みません。その場合は状態を確認し、Actionsのdeployで起動します。

## 6. 更新時の注意と復旧

対戦状態はメモリ上にあるため、対戦サーバーの再起動で部屋と進行中の対戦は失われます。更新は対戦中の人がいないタイミングで行います。既存対戦を永続化して継続する仕組みはありません。

配布前の検証に失敗した場合は旧版を維持します。切り替え中の失敗では管理済みの旧版へ戻す処理があります。ただし公開URLの通信確認だけが失敗した場合は警告となり、自動で戻すとは限りません。ActionsのSummaryと対象ログを確認し、最新のmain・配布SHA・稼働状態を照合します。

診断で正常応答が戻ること、実際の2人対戦が成立することを順に確認します。多人数の同時負荷は別途測定が必要です。再接続・復帰があることを、データベース保存や無期限の復帰保証と混同しません。

## 7. 文書の扱い

最新版は docs/latest、旧企画・過去検証・分析は docs/archive/2026-10-07 に保存します。元の資料パスには最新版とバックアップへの案内を残しています。過去の検証成功はその時点の記録であり、現在の版の成功を保証しません。

通常カード一覧はデータと表示用の効果文から抽出しています。今後カードを変更した際は一覧も更新し、Word版とMarkdown版を同じ日付・内容に揃えます。
