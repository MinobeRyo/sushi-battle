# PHP経由の配置手順

更新日：2026年10月7日。通常運用はGitHub Actionsによる転送とPM2再起動です。この資料は配布物の構成と、手動配置が必要になった場合の手順を説明します。過去の手動起動記録は[旧版バックアップ](archive/2026-10-07/PHP経由の配置手順_バックアップ_2026-10-07.md)にあります。

## 通信の構成

公開画面から `api.php` へ短いHTTP要求を送り、同じサーバー内のNode.jsへ中継します。対戦のルール・部屋・参加者の検証はNode.jsが担当します。PHPファイルだけではオンライン対戦は動きません。

通常更新は[GitHub Actions自動デプロイ](GitHub%20Actions自動デプロイ.md)を参照してください。手動の `npm run server` をPM2稼働中の同じポートに重ねて起動しません。

## 配布物を作る

開発用Node.js 24の環境で、プロジェクトルートから実行します。

```bash
npm ci
node scripts/package-gms.mjs
```

`release/gms` にPHP通信を選んだ画面、`api.php`、対戦プログラム、配置スクリプトなどが生成されます。

| 配布物 | 手動配置の場合の場所 |
| --- | --- |
| release/gms/sushi-battle の中身 | /home/h0/ryom13/public_html/sushi-battle/ |
| release/gms/sushi-battle-server の中身 | /home/h0/ryom13/sushi-battle-server/ |

これは旧来の手動配置先です。現在の自動配布は専用の配布履歴とPM2を使うため、通常はこの手順で上書きしません。手動へ戻す場合は現在の管理方式、待受ポート、復旧方法を確認してから切り替えます。

公開先の直下には `index.html`、`api.php`、`assets` が並びます。対戦プログラム側には `package.json`、`package-lock.json`、`server`、`src` が並びます。フォルダを二重にしないようにします。

## 手動起動が必要な場合

対戦中の人がいないこと、既存の管理プロセスと競合しないことを確認してから、手動配置先で実行します。再起動で進行中の部屋は失われます。

```bash
cd /home/h0/ryom13/sushi-battle-server
npm ci --omit=dev
HOST=127.0.0.1 PORT=3001 SUSHI_ALLOWED_ORIGINS=https://gms.gdl.jp npm run server
```

手動起動は端末を閉じると止まる可能性があります。通常の継続運用は専用PM2の自動配置へ戻します。既存の別プロセスを、ポート番号だけを理由に停止しません。

## 配置後に確認する

1. [公開通信の確認](https://gms.gdl.jp/~ryom13/sushi-battle/api.php)で `ok: true` と `transport: php-polling` が返ることを確認します。
2. [ゲーム](https://gms.gdl.jp/~ryom13/sushi-battle/)を再読み込みし、部屋を作成します。
3. 別ブラウザまたは別端末で部屋コードを入力し、購入・召喚・ターン交代が両方に反映されることを確認します。
4. 再読み込みによる復帰と、配置用SSHの終了後も起動していることを確認します。

診断応答の成功だけでは、実際の対戦確認を代替しません。古い対戦プログラムで期待する通信形式に対応していない場合は503になります。

## 通信の範囲

対戦中は画面ごとにおおむね1秒おきに状態を確認します。待機・非表示では間隔を伸ばし、失敗時は再接続間隔を広げます。前の要求が終わるまで次を重ねません。通信断やブラウザ休止の検知は即時ではなく、復帰猶予を過ぎれば部屋が閉じられます。

相手の手札・山札順・参加用トークンは公開状態へ含めません。操作の手番、AP、所有権、再送はサーバーで検証します。PHPの中継先は `127.0.0.1:3001` の所定パスに固定し、任意のURLやコマンドは受け付けません。本文サイズ・待機時間・POST元を制限します。

多人数の同時負荷は別途測定が必要です。利用人数を増やすときは応答時間とサーバー負荷を確認してください。
