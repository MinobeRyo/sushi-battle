# GitHub Actionsによる自動デプロイ

更新日：2026年10月7日。現在のワークフロー実装に沿った通常運用の手順です。初回設定の記録は[旧版バックアップ](archive/2026-10-07/GitHub%20Actions自動デプロイ_バックアップ_2026-10-07.md)に保存しています。鍵・Secretsが登録済みなら、更新のたびに作り直しません。

## 通常の更新

1. 作業ブランチへ変更をコミットし、main向けにPRを作成します。作業中はDraftにします。
2. `Build and deploy to GMS` のテスト・型確認・lint・配布物作成が成功したことを確認します。
3. 公開してよい段階でDraftを解除します。同一リポジトリの通常PRは `Merge verified pull requests` が検証済みSHAを指定してマージを試みます。
4. mainへの反映後、`GMS_AUTO_DEPLOY=true` なら配布に進みます。自動マージからの配布は `workflow_dispatch` で明示的に起動します。
5. Actionsのbuild・deployとSummaryを確認し、[公開ゲーム](https://gms.gdl.jp/~ryom13/sushi-battle/)で2人対戦を確認します。

Draft、外部フォーク、失敗・中断したチェック、検証後に新しいコミットが追加されたPRは自動マージしません。必須レビュー・ブランチ保護・競合の条件も満たす必要があります。手元の保存やコミットだけでは公開されません。

## 手動の診断と配布

[Actions](https://github.com/MinobeRyo/sushi-battle/actions)から `Build and deploy to GMS` の `Run workflow` を開き、mainを指定します。

| operation | 動作 |
| --- | --- |
| check | SSH、Node.js、npm、配置先の権限を確認。現在の対戦サーバーと公開PHPの状態も診断。転送・停止・再起動はしない |
| deploy | テスト・ビルド後に転送し、専用PM2で対戦サーバーを起動または再起動 |

`check`の準備確認成功と、ゲームが現在稼働していることは別です。現在停止している場合も診断を読んでからdeployへ進みます。公開側は[api.php](https://gms.gdl.jp/~ryom13/sushi-battle/api.php)の正常応答に加え、実際の部屋参加・召喚・ターン交代・再読み込み後の復帰を確認します。

## 必要な設定

| 設定 | 役割 |
| --- | --- |
| Secret: GMS_SSH_KEY | 自動化専用のSSH秘密鍵 |
| Secret: GMS_KNOWN_HOSTS | 確認済みのサーバーのホスト公開鍵 |
| Variable: GMS_AUTO_DEPLOY | trueならmainへのpushで自動配布。falseなら自動配布を停止 |

初回の鍵作成・公開鍵登録・Secrets設定は[旧版の初回手順](archive/2026-10-07/GitHub%20Actions自動デプロイ_バックアップ_2026-10-07.md)を参照します。過去に実行した記録と、今から行う操作を区別してください。秘密鍵をリポジトリやチャットへ記載せず、ホスト確認を無効化しません。

## 配置と再起動

`node scripts/package-gms.mjs` がPHP通信を選択したフロント、`api.php`、対戦プログラム、配置スクリプトをまとめます。CIは同じ配布物を利用します。

- 公開画面：`/home/h0/ryom13/public_html/sushi-battle`
- 配布履歴・専用PM2情報：`/home/h0/ryom13/.sushi-battle-deploy`
- 対戦プログラム：`127.0.0.1:3001`
- 旧公開画面：同じpublic_html内の`.sushi-battle-previous-*`

配置スクリプトは専用のPM2管理情報を使い、他のアプリのPM2は操作しません。管理外のプログラムが3001番ポートを使用している場合は、自動で停止せずエラーにします。

対戦状態はメモリ上にあるため、再起動すると進行中の部屋は失われます。対戦中の人がいない時間に更新します。サーバー本体の再起動に連動するOS設定は含みません。必要になった場合は、状態を確認してActionsのdeployを実行します。

## 失敗したとき

配布前の検証で失敗した場合は旧版を維持します。切り替え中の失敗では管理済みの旧版へ戻す処理があります。公開PHPの確認だけが失敗した場合は警告となるため、Summaryで本体の起動結果と公開側の診断を分けて確認します。確認せずに連続で再配布しません。

公開結果の基準は最新のActions実行と公開画面です。以前の成功記録だけで現在の稼働を判断しません。配布履歴・ログは自動削除しないため、継続運用では容量を確認します。
