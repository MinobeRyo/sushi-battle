# 自動デプロイの実行フロー

更新日：2026年10月7日。初回設定は通常の更新作業と分けています。[2026年9月の初回設定記録](archive/2026-10-07/自動デプロイの実行フロー_バックアップ_2026-10-07.md)は履歴として保管しています。

## 通常の更新

1. 作業ブランチへ変更をコミットしてpushします。
2. main向けのPRを作成します。作業中はDraftです。
3. GitHub Actionsでゲーム・オンライン・PHP・配置復旧のテスト、型確認、lint、ビルドが実行されます。
4. チェック成功後、通常PRは自動マージの対象です。必須レビュー、保護ルール、競合、コミットの一致も確認されます。
5. main反映後、`GMS_AUTO_DEPLOY=true` なら配布物の転送と専用PM2による再起動へ進みます。
6. ActionsのSummaryと公開画面を確認します。別ブラウザの2画面で部屋参加・召喚・ターン交代・再読み込み復帰を試します。

自動マージから配布を開始する処理は `workflow_dispatch` を利用します。mainへ直接pushした場合も、変数がtrueなら配布対象です。手元の保存、ローカルコミット、Cyberduckでのファイル転送だけでは、この自動起動フローは動きません。

## 手動実行を選ぶ場合

| 目的 | 操作 |
| --- | --- |
| 接続と配置準備を調べる | mainで `operation: check` |
| 停止中のプログラムを配置・起動する | mainで `operation: deploy` |
| 自動配布だけを止める | リポジトリ変数 `GMS_AUTO_DEPLOY=false` |
| 自動マージを止める | `Merge verified pull requests` ワークフローを無効化 |

checkは転送・停止・再起動をしません。ゲームが停止中でも配置準備が成功する場合があります。deployは新版の起動と応答を確認します。

## 更新前後の確認

再起動でメモリ上の部屋・対戦は失われるため、遊んでいる人がいない時間に更新します。配布前に失敗した場合は旧版を維持します。切り替え失敗時には管理済みの旧版へ戻す処理がありますが、公開URLの診断だけが失敗した場合は自動復旧とは限りません。Summaryとログを読んで対応します。

PM2はターミナルとは別に動きますが、サーバー本体再起動後のOS自動起動設定は含みません。サーバー再起動後は必要に応じてActionsのdeployを実行します。

Secretsの用意や初回切り替えをやり直す場合は[詳細手順](GitHub%20Actions自動デプロイ.md)から旧版の設定記録へ進んでください。設定済みの鍵を毎回作成したり、稼働中のサーバーを準備段階で止めたりする必要はありません。
